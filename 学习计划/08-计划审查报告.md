## 0. 一句话结论

**这套计划的"骨架"是对的**——AI 领读式编程、只学 GDScript 一门语言、12 周必须发出去、交付物硬性化、每天讲 10 行代码，这五个决策都踩在点上，很多自学者栽的坑它提前堵住了。

**但它有一个系统性盲区**：整套计划是**按"网络畅通、软件都能顺利下载"的理想环境写的**，而你 Day 01 就实测撞上了两道墙——GitHub 下载通道被阻断、Git 授权弹窗反复失败。计划里至少 **20 处**依赖下载（Godot、官方 demo、素材包、导出模板、字体……），**全部没有预案**。这是当前最大风险，不是"可能会出问题"，是"已经出过问题、后面还会再出"。

另外还有一批**自相矛盾**的地方（文档说 A，实际是 B；文档这里说 A，那里说 C），会让执行时反复困惑。

## 2. P0 · 阻断级问题（不改会直接卡住）

### P0-1 ⭐ 网络可达性完全没有纳入设计（最严重）

**证据**：`D:\dev\ai-game-learning\学习日志.md` 里你自己记的——

> 「GitHub 下载通道被阻断（换清华镜像）、git 授权弹窗反复失败（改用 Token）」

**问题**：整个计划里，需要"下载"的动作至少有 20 处：
- Godot 引擎本体（Day 08）
- 导出模板（Day 34，几百 MB～1 GB）
- 官方 demo 合集 / 别人的项目（Day 11、23、26、29）
- 素材包：itch.io、Kenney、OpenGameArt（Day 26、36）
- 免费像素字体（Day 39）
- 上传发布相关（Day 78）

**这些动作全部默认"点一下就下好了"**，而你的实测环境不是这样。**这会在 Day 08（装 Godot）就开始卡，一路卡到 Day 78。**

**已做修订**：在 `05-环境搭建清单.md` 开头**新增"第 0 节 · 先解决网络"**，含四个可操作方案：
1. **git 克隆走镜像**（清华镜像 / ghproxy 加速）
2. **下载 ZIP 用加速前缀**
3. **Godot 与导出模板的备用下载**（走 GitHub Release）
4. **Git 认证改用 Token**（别跟弹窗死磕）

并加了"什么时候该怀疑是网络问题"的判据。

### P0-2 ⭐ Godot 版本没有锁定，会引发连锁报错

**证据**：`05` 只说"Godot 4.x 标准版"；`01` Day 28 说"`TileMapLayer`（Godot 4.3+）或在旧版本用 `TileMap`"。

**问题**：Godot 4.x 的**小版本差异比想象中大**：
- **4.3** 才引入 `TileMapLayer`；**4.4 起 `TileMap` 被官方废弃**
- 其他节点/语法在不同小版本间也有调整

后果：**AI 生成的代码、网上教程、AssetLib 里的项目，只要小版本和你不同，就报一堆莫名其妙的错**，而新手根本不会想到是版本问题——这是最容易"卡死并放弃"的一类问题。

**已做修订**：`05` C2 改为**"确认并锁定版本"**，要求：精确记到小版本（如 `4.5.stable`）、整个 12 周不升级、看教程先核对版本。`01` Day 08 同步加了"记版本号"步骤，Day 28 改为按锁定版本选节点。

### P0-5 `day01-setup.cmd` 把 Git 路径写死（已修）

**证据**：脚本里 `set "GIT=D:\dev\Git\cmd\git.exe"`，路径写死。

**问题**：本机恰好装在 `D:\dev\Git`，所以现在能跑。但**只要换机器、重装 Git 到默认位置（`C:\Program Files\Git`），脚本就立刻报 `[ERROR] git not found`**。而且 `05` A1 还写着"全部保持默认，一路 Next"——**文档说默认，脚本却写死非默认路径，自相矛盾**。

**已做修订**：脚本改为**自动探测**——先查 PATH（`where git`），再依次回退到 `D:\dev\Git`、`C:\Program Files\Git`、`%LOCALAPPDATA%\Programs\Git`，全找不到才报错并给出安装指引。`05` A1 也改成注明"本机实际装在 `D:\dev\Git`"。

## 3. P1 · 逻辑与一致性问题

### 进度与时间体系

**P1-1 Day 编号与"周日休息"的日历映射冲突**
- `00` 规则：周一～周五做任务、周六整合、周日只复盘
- `01` 却是 **Day 01～84 连续编号**，每第 7 天（Day 07、14、20…）标"周整合"
- **若 Day 01 是周一，那 Day 07 就是周日**——与"周日只复盘"矛盾
- **已做修订**：`01` 头部补充说明（见文件开头"怎么用这份表"），明确"每 7 天一个循环，第 7 天 = 整合 + 复盘，不强制休息"

**P1-2 ⭐ 时间预算与任务量严重不匹配（会持续"落后"）**
- `00`/`06` 说"计划每周 10 小时"
- 实际把 `01` 的分钟数加起来：

| 周 | 任务量合计 | 对比"10 小时" |
|---|---|---|
| 第 1 周 | 11.5 h | 超 15% |
| 第 2 周 | 12.5 h | 超 25% |
| 第 5 周 | 15 h | **超 50%** |
| 第 9 周 | **18 h** | **超 80%** |

- **问题**：计划一边说"允许落后，周末补"，一边**把每周任务量定得必然落后**。到第 5～9 周，落后会累积成"永远补不完"，这是弃坑的标准路径。
- **建议（二选一，需你决定）**：
  - **A. 上调预算**：把复盘表的"计划 10 小时"改成"计划 14～18 小时"，并在 `00` 明确"第 5 周起强度上升"
  - **B. 砍任务量**：把第 9～12 周的 Day 内容再削（例如 Day 57～59 从三天压到两天，Day 62～68 只做 2 关）
- **我的建议是 A + 少量 B**：新手在"落后"状态下的心理损耗，比"多花 4 小时"大得多。**宁可预算写高，也不要让你天天觉得欠账。**

**P1-3 里程碑体系"双轨"冲突**
- `06` 模板列了 **7 个**：M0 / M0.5 / M1 / M1.5 / M2 / M2.5 / M3
- `00` 只定义 **4 个**：M0～M3
- 你自己的 `学习日志.md` 用的是 **4 个**版本
- 且 `06` 的 **M2.5 标"第 9 周末 跑通 API"，但 API 任务是 Day 46～47，属于第 7 周**——时间错位
- **已做修订**：`06` 统一为 **4 个正式里程碑（M0～M3）**，其余降级为"顺路检查点"，并修正了 API 检查点的时间
